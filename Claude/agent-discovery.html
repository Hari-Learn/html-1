Dynamic Tool Discovery

How Claude finds the right tool without loading every tool upfront.

1. Understand with an analogy

Imagine entering a huge supermarket with 10,000 products.

Instead of reading every product label, you first search for "milk".

Dynamic tool discovery works similarly: search for relevant tools instead of exposing every tool immediately.

2. What is the problem with too many tools?

  • Large tool definitions consume context tokens.
  • Similar tool descriptions can confuse selection.
  • More tools can increase prompt complexity.
  • Maintaining a huge tool catalogue becomes difficult.
  • Tool selection can become less reliable.
Remember: More available tools do not automatically mean a better agent.

3. Traditional vs dynamic tool loading

Traditional approach

Load all 200 tool definitions into the model context.

Tool 1 + Tool 2 + Tool 3 + ... + Tool 200

Large initial context requirement.

Dynamic approach

Start with a tool-search capability.

Search → Find relevant tool → Load definition → Use tool

Only relevant definitions are loaded when needed.

4. Example: Banking assistant

Imagine an assistant with 100 banking tools.

Customer says: "Show my recent transactions."

Step 1: Search available tools for transaction history.
↓
Step 2: Discover get_transactions.
↓
Step 3: Load its description and input schema.
↓
Step 4: Call the tool with authorized account context.
↓
Step 5: Present the returned transactions.

5. Tool Search is not Tool Execution

Action Purpose
Tool Search Finds a relevant tool.
Tool Loading Makes the selected tool definition available.
Tool Execution Actually performs the requested operation.

Finding a tool does not mean that the tool has executed.

6. Important design considerations

  • Clear descriptions: Explain what each tool does and when it should be used.
  • Specific schemas: Define required parameters accurately.
  • Permission checks: Discovering a tool must not grant permission to use it.
  • Tool governance: Restrict sensitive operations using application-side authorization.
  • Observability: Track searches, selections, calls and failures.

7. Rare concept: Deferred tool loading

A deferred tool is not fully exposed to the model at the beginning.

Its full definition can be made available later when the agent discovers that it needs it.

This can reduce the initial context cost when working with a very large tool catalogue.

Memory trick: Search first, load later, execute only when appropriate.

8. Exam scenario

A company gives Claude 300 tool definitions at the start of every conversation. The context is becoming large, and many tools are irrelevant to each request.

Which design improvement is most appropriate?

Reveal answer

Introduce tool search or dynamic discovery so relevant tool definitions are loaded when needed. Maintain separate authorization checks for actual tool execution.

9. Five points to remember

  1. Too many tool definitions can consume context.
  2. Tool search discovers relevant capabilities.
  3. Deferred loading reduces upfront definitions.
  4. Discovery is different from execution.
  5. Authorization must still be enforced separately.
