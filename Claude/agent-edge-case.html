Structured Output: JSON Schema Edge Cases

Handling optional fields, null values, enums and nested structures.

1. Why Structured Output?

Suppose Claude must classify customer complaints. Your backend expects a predictable JSON object rather than a paragraph.

{
  "category": "delivery",
  "priority": "high",
  "requires_human": true
}

Structured output makes it easier for software to parse and use model responses.

ELI10 analogy

Instead of asking someone to write an essay, you give them a form with fixed fields. Everyone returns information in the same format.

2. Required vs Optional Fields

A required field must be supplied. An optional field may be omitted if the schema permits it.

Required

{
  "name": "Arun",
  "age": 30
}

Both fields are expected.

Optional

{
  "name": "Arun"
}

Age may be omitted if the schema allows it.

3. Missing vs Null vs Empty String

These three values are not interchangeable.

Missing field

{"name":"Arun"}

The field was not supplied.

Null value

{"age":null}

The field exists but has no value.

Empty string

{"name":""}

The field contains a string with zero characters.

Exam trap: A nullable field is not necessarily optional. A required field may still need to appear even when its value is null.

4. Enum Constraints

An enum restricts a field to a predefined set of allowed values.

{
  "priority": {
    "type": "string",
    "enum": ["low", "medium", "high"]
  }
}

Allowed: low, medium, high.

Not allowed: urgent, critical, normal.

Enums are useful when downstream software expects a controlled vocabulary.

5. Nested Objects and Arrays

Real applications often need complex structures.

{
  "customer": {
    "name": "Arun",
    "verified": true
  },
  "issues": [
    "late_delivery",
    "damaged_package"
  ]
}

Here, customer is a nested object and issues is an array of values.

Important: Validate nested fields and array elements too, not just the outer JSON object.

6. Additional Constraints

Minimum / maximum

A refund amount might be constrained to a permitted numerical range.

String length

A customer ID or description can have length restrictions.

Array length

A response may permit no more than five suggested products.

Pattern

An identifier may need to follow a specific format.

Not every JSON Schema keyword is supported by every constrained-output implementation. Check the specific API's supported schema subset.

7. Schema Validity vs Business Validity

Consider this response:

{
  "refund_amount": 50000,
  "currency": "INR"
}

It may be structurally valid JSON.

But it may still violate the customer's refund eligibility.

JSON Schema checks structure. Backend business logic checks whether the operation is allowed.

8. CCAO-F Scenario Challenge

Your application requires a JSON field named delivery_date. Sometimes the date is unknown. The developer makes the field required and allows it to contain either a valid date string or null. Claude omits the field whenever the date is unknown, causing validation failures.

What is the BEST fix?

A. Remove JSON validation entirely.

B. Make the field optional but keep it required in the backend.

C. Instruct the model to include delivery_date with null when unknown, and ensure the schema permits null for that required field.

D. Replace null with the current date.

Reveal answer

Correct answer: C

Required means the field must appear. Nullable means the field can contain null. The correct schema and instructions must express both requirements.

9. Notebook Revision

  • Structured output = predictable data format.
  • Required = field must appear.
  • Optional = field may be omitted.
  • Nullable = field may contain null.
  • Empty string is not the same as null.
  • Enum = allowed fixed values.
  • Nested structures also require validation.
  • Schema validity does not guarantee business validity.
