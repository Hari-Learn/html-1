Advanced Tool-Result Handling

Understanding tool IDs, error results and safe recovery.

1. Tool call is not the same as tool success

Imagine asking a bank employee to transfer ₹5,000.

The employee accepting your request does not mean the money has been transferred.

Tool call

Claude requests an action.

Tool result

The tool reports what happened.

Always inspect the result before claiming success.

2. Understand tool_use_id

Every tool call has an identifier. The corresponding tool result must refer to that same identifier.

{
  "type": "tool_use",
  "id": "toolu_123",
  "name": "lookup_order",
  "input": {
    "order_id": "ORD-100"
  }
}
↓
{
  "type": "tool_result",
  "tool_use_id": "toolu_123",
  "content": "Order found"
}

The result's tool_use_id connects it to the original call.

3. What does is_error mean?

In a tool-result block, is_error indicates whether the tool execution reported an error.

is_error: false

The tool did not report an execution error.

is_error: true

The tool reports an execution error. Claude can use that information to recover or explain the problem.

A non-error result still needs to be checked for business meaning. For example, "order not found" may be a valid lookup outcome rather than a technical failure.

4. Three different failure categories

Protocol error

Invalid request structure, invalid parameters or protocol-level problems.

Tool execution error

The tool was called but could not complete its operation.

Business outcome

The tool worked correctly but returned a result such as "refund not eligible".

Do not treat every negative business outcome as a technical error.

5. Partial failure in multiple tools

Suppose Claude needs to perform three independent operations:

Tool A

Success

Tool B

Failure

Tool C

Success

The entire workflow is not automatically successful just because two tools succeeded.

The application should track each result, decide whether the failed step can be retried and avoid repeating completed side effects.

6. Safe recovery patterns

  • Validate: Check tool arguments before execution.
  • Correlate: Match each result to its correct tool call ID.
  • Classify: Identify protocol, execution or business errors.
  • Retry carefully: Retry transient failures only when safe.
  • Use idempotency: Prevent duplicate side effects during retries.
  • Escalate: Send unresolved or sensitive cases to a human.

7. Exam scenario

Claude calls a refund tool. The backend times out. The application does not know whether the refund was processed.

Which is the safest next step?

Reveal answer

Check the refund's transaction status using a reliable lookup mechanism. If a retry is needed, use an idempotency key or equivalent duplicate-prevention control. Do not claim success until confirmed.

8. Final notebook summary

tool_use = Claude asks a tool to do something.

tool_result = Tool returns its outcome.

tool_use_id = Connects the result to its call.

is_error = Indicates an execution error in the result.

Idempotency = Helps prevent duplicate effects.
