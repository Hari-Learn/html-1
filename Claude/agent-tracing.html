API Request Metadata & Distributed Tracing

How to trace a request across Claude, tools and backend services.

1. What is Request Metadata?

Metadata is additional information associated with an API request. It helps identify, organise and investigate requests.

Example:

{
  "model": "your-selected-model",
  "max_tokens": 1024,
  "metadata": {
    "user_id": "user_123",
    "session_id": "session_456"
  }
}

This is an illustrative request structure. Use the actual API schema supported by the endpoint you are calling.

ELI10 analogy

A courier package has a tracking number, sender details and destination. These details help locate the package when something goes wrong. API metadata serves a similar identification purpose.

2. What is a Request ID?

A request ID is a unique identifier associated with an individual API request. It helps support teams and developers locate a particular request in logs or provider-side diagnostics.

Illustrative response header

request-id: req_abc123xyz

If an API request fails, record the request ID along with the error, timestamp and relevant application context.

Exam trap: A request ID identifies an API request. It is not automatically the same as a user ID or conversation ID.

3. What is Distributed Tracing?

In an agent application, one customer request may travel through multiple services.

Customer request

↓

Application backend

↓

Claude API

↓

Order lookup tool

Payment service

↓

Final response

Distributed tracing follows the journey across these components so you can understand where the request slowed down or failed.

4. Trace ID vs Span ID

Trace ID

Identifies the entire journey of a request across multiple services.

trace_id = trace_001

Span ID

Identifies one individual operation within that journey.

span_id = span_002

One trace can contain many spans. For example, one span for the Claude API call, another for order lookup and another for refund processing.

Easy memory trick

Trace ID = whole journey. Span ID = one step in the journey.

5. Example: Finding a Slow Agent

A customer reports that a refund took 12 seconds. Your monitoring system shows:

OperationDuration
Application processing0.5 sec
Claude API call2 sec
Order lookup tool1 sec
Payment service8.5 sec
Total12 sec

Finding: The payment service is the main bottleneck.

Without tracing, developers might waste time optimising Claude when the actual delay is in the payment service.

6. What Should You Log?

  • Trace ID and span ID.
  • API request ID, when available.
  • Timestamp and operation name.
  • Model identifier and application version.
  • Latency and token usage.
  • Tool name, outcome and error category.
  • Retry count and final status.

Privacy warning

Do not log API keys, passwords, access tokens or unnecessary personal data. Redact sensitive information and restrict access to logs.

7. Logging vs Metrics vs Traces

Logs – What happened?

Example: Refund tool returned a timeout error.

Metrics – How much or how often?

Example: 8% of refund requests timed out.

Traces – Where did it happen?

Example: The payment service caused most of the delay.

8. CCAO-F Scenario Challenge

A Claude-powered banking assistant sometimes takes 15 seconds to answer. The application uses Claude, an account lookup tool and a transaction service. Developers know the total response time but cannot identify which component causes the delay.

What is the BEST solution?

A. Increase the model's maximum token limit.

B. Add distributed tracing with trace IDs and spans across the model call and backend tools.

C. Increase the number of application servers immediately.

D. Disable all logs to improve response speed.

Reveal answer

Correct answer: B

The problem is identifying the bottleneck. Distributed tracing reveals the time spent in each component before deciding what to optimise.

9. Notebook Revision

  • Metadata = additional request information.
  • Request ID = identifier for an individual API request.
  • Trace ID = identifier for the entire request journey.
  • Span ID = identifier for an individual operation.
  • Logs = events and details.
  • Metrics = numerical measurements.
  • Traces = flow and timing across services.
  • Never expose secrets in logs or metadata.
