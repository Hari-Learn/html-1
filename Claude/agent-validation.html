Page 53: Tool Argument Validation & Schema Evolution

How to prevent invalid tool calls and safely change tool definitions.

1. What is Tool Argument Validation?

Imagine Claude is a customer-support employee. Claude asks the backend to process a refund.

The backend expects:

  • A valid order ID
  • A refund amount greater than zero
  • A supported currency
  • An authenticated customer

Validation checks whether the input satisfies these requirements before the tool performs its action.

ELI10 analogy

A railway ticket checker verifies your ticket before allowing you to board. A tool validator checks the arguments before allowing an operation.

2. Four Levels of Validation

Level 1 – Type validation

Is the input the correct data type?

Example: refund_amount must be a number, not "five hundred".

Level 2 – Format validation

Does the input follow the required format?

Example: order_id must follow the expected ID pattern.

Level 3 – Business-rule validation

Is the requested operation allowed?

Example: refund amount cannot exceed the eligible order amount.

Level 4 – Authorization validation

Is this user allowed to perform the operation?

Example: a customer cannot refund another customer's order.

3. Schema vs Runtime Validation

A tool schema describes the expected input structure. Runtime validation checks the actual request against real-world rules.

Schema validation Runtime validation
Is amount a number? Is the amount refundable?
Is order_id present? Does this order exist?
Is currency a string? Is that currency supported?

Exam trap: A valid JSON tool call does not automatically mean the operation is safe or authorized.

4. What is Schema Evolution?

Schema evolution means changing a tool's input or output structure as the application grows.

Example: Version 1

{
  "order_id": "ORD123"
}

Version 2

{
  "order_id": "ORD123",
  "reason": "damaged_item",
  "currency": "INR"
}

The new version introduces additional fields. Older agents or integrations may not know about them.

5. Backward Compatibility

A change is backward-compatible when existing clients can continue working without modification.

Usually safer

  • Add an optional field
  • Add a new optional response field
  • Support old and new formats temporarily

Potentially breaking

  • Rename a required field
  • Remove an existing field
  • Change a field's data type
  • Change the meaning of an existing field

6. Safe Tool Schema Migration

1

Introduce the new schema

Add new fields without immediately removing old ones.

2

Update tool descriptions

Tell Claude what the new fields mean and when to use them.

3

Test old and new clients

Check whether both versions behave correctly.

4

Monitor failures

Track validation errors and unexpected tool responses.

5

Deprecate old fields carefully

Remove them only after dependent clients have migrated.

7. Common Production Failure

Claude sends a refund request with a valid order ID but an amount of ₹50,000. The actual eligible refund is only ₹2,000.

Incorrect approach

Trust the tool call because the JSON is valid and the order ID exists.

Correct approach

The backend independently checks the order, customer authorization, refund eligibility and maximum refundable amount before processing.

Remember: Claude can propose an action. The backend must enforce the rules.

8. CCAO-F Scenario Challenge

A company updates its refund tool. Previously, it accepted only order_id. The new version requires order_id and refund_reason. After deployment, some Claude agents still send only order_id, causing tool failures.

What is the BEST engineering response?

A. Increase Claude's temperature so it explores more arguments.
B. Retry every failed request repeatedly.
C. Update agent tool definitions and descriptions, validate the migration with old and new clients, and maintain compatibility where needed.
D. Disable validation so all requests are accepted.
Reveal answer and explanation

Correct answer: C

This is a schema compatibility problem, not a creativity or retry problem. The agent must understand the updated contract, and the application must test compatibility before rollout.

Why not B? Retrying the same invalid request will not fix a missing required field.

9. Quick Revision Notes

  • ✓ Schema = expected structure of tool input/output.
  • ✓ Validation = checking whether the request is acceptable.
  • ✓ Runtime checks = real-world rules and authorization.
  • ✓ Schema evolution = changing tool contracts over time.
  • ✓ Backward compatibility = old clients continue working.
  • ✓ Breaking change = old clients may fail.
  • ✓ Never rely only on Claude to enforce security or business rules.
  • ✓ Repeatedly retrying invalid input does not solve a schema mismatch.
